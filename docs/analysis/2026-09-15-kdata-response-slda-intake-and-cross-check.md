## 7. 문언 충돌과 과잉확정 방지

### 7.1 동일인 연결

D2는 복덕판 신청서상 이사 지위를 수신인인 “귀하”에게 귀속했다. D4는 두 신청서의 성명을 확인해 모두 “귀하의 개인정보”임을 인식했다고 하면서도 별도 동일인 확인이나 새 연결 처리는 없었다고 진술한다. 문언상 동일 인물 귀속 판단이 수행됐다는 관찰은 강하게 지지된다. 다만 그 행위가 개인정보보호법상 별도의 “결합 처리”인지 여부는 이 분석에서 판단하지 않는다.

### 7.2 1월 접근과 8월 참조

D5의 8월 참조 자인으로 “8월에는 1월 관련 자료를 참조하지 않았다”는 가능성은 배제된다. 그러나 다음 중 무엇인지는 아직 분리되지 않는다.

- 1월 회신 문서를 8월에 다시 열람
- 1월에 만든 별도 작업물을 보존해 사용
- 신청서류를 8월에 다시 조회
- 담당자 기억과 기존 회신문만 사용

따라서 “파생정보 보유 부정”과의 충돌은 강한 검증 쟁점이지만, 참조 객체·저장 위치·열람로그가 없으면 기술적 저장·재조회 형태까지 확정할 수 없다.

### 7.3 구두협의와 기록 부존재

구두협의가 있었고 기록이 없다는 두 진술은 논리적으로 양립할 수 있다. 여기서 확정되는 것은 “기관이 무기록 구두협의를 공식 설명으로 제시했다”는 사실이다. 협의 자체의 실재와 내용은 참여자·일시·안건·후속행위로 보강해야 한다.

### 7.4 전자결재의 열람·저장 유형

“열람·저장 유형으로 관리”라는 문구만으로 문서별 사용자 접근로그가 현재 보존돼 있다고 단정하지 않는다. 데이터 유형 분류, 이벤트 로그, 사용자 감사로그는 서로 다른 기록일 수 있다. 화면과 후속 청구에서는 이 문구를 “사용자별 열람 기록 존재 확정”으로 표시하지 않는다.

## 8. 전달 문서의 형식·채널 이상

현재 자료는 9월 15일 답변서가 정보보호인프라팀 담당자의 이메일과 암호화 첨부로 전달됐으나 문서 자체에 작성 부서·결재선·시행 문서번호가 없었다는 점을 지적한다. 이는 다음 두 사실을 구분해 기록한다.

- 이메일을 통해 해당 파일을 수령한 사실: 전달 메타데이터로 확인 가능
- 그 파일이 전자문서시스템에서 정식 기안·결재·시행된 문서인지: 현재 `insufficient`

사용자가 제공한 이메일 표시본에는 서명란의 표시 이메일과 링크 대상 계정이 서로 다른 메타데이터 이상도 보인다. 다만 복사·붙여넣기 또는 웹메일 링크 생성 과정에서 생겼을 수 있으므로 원본 MIME의 `From`, `Reply-To`, 링크 HTML과 발송 서버 헤더를 확보하기 전에는 발신 이상으로 확정하지 않는다.

8. 평가점수·평가의견·자동 제외·결격코드·상태변경 전후값과 변경자·변경시각

## 10. 저장소·DB 반영 결정

- 세 첨부 원문은 공개 Git 저장소에 넣지 않는다.
- 이 문서를 향후 루브릭 기반 evaluation run 생성 전의 검토 입력으로 사용한다.
- F-03·F-04는 새 근거로 강화하되 기존 판정 행을 덮어쓰지 않고 새 evaluation run에서 변경사유를 남긴다.
- I-01~I-04와 U-01은 현재 단계에서 임의 승격하지 않는다.
- 원문 대조가 끝나기 전 파생 CSV의 문장을 `source_grade=A`로 올리지 않는다.
- 공개 화면 상수는 이 기록만으로 바로 수정하지 않는다. RLS·공개 View 확정 후 DB에 증거·루브릭 입력·게이트 결과를 적재하고 검산한 다음 승인된 최신 run을 화면에 반영한다.

이 분석 과정에서는 Supabase와 운영 데이터를 변경하지 않았다.
