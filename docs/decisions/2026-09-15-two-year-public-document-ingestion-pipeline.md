# 2026-09-15 2년 공개문서 수집·분석 파이프라인 결정

## 결정 상태

채택·코드 구현. Supabase migration은 원격에 적용하지 않음.

## 목적

K-DATA와 신용보증기금의 공개문서를 향후 2년간 동일한 검증규약으로 반복 수집한다. 파서 코드는 재사용할 수 있지만 두 기관의 저장소·Supabase 프로젝트·수집 프로필·실행 산출물은 섞지 않는다.

## 채택한 체인

`원본 → SHA-256 → 형식/보호 분류 → 전문 추출 → 정규화 → 문장 단위 → 내부 매칭 → 추출 신뢰도 → 공개 투영`

### 지원 형식과 보호문서 처리

- HWPX는 ZIP/XML 구조로 추출한다.
- HWP는 OLE 파일 헤더와 본문 레코드를 읽는다.
- PDF는 텍스트 계층을 추출하고, 텍스트가 없으면 OCR 필요 상태로 분기한다.
- DRMONE·FASOO 표식은 자동 분류하되 보호 우회·해제·암호 추측은 하지 않는다.
- 보호문서는 원본 해시, 탐지 공급자, 탐지 근거, `protected` 상태만 남겨 수동 적법 처리 대기열로 보낸다.

## 신뢰도 의미

`extraction_confidence`는 형식 탐지, 추출 완전성, 글자 품질, 사전에 선언한 내부 용어 일치율로 계산한다. 이 값은 **전문 추출 품질**만 설명한다. 문서의 진실성, 특정 주장에 대한 사실지지, 탈락 인과관계의 확률을 대신하지 않는다. 사실 판단은 기존 13개 기준·9개 게이트의 별도 `evaluation_run`에서만 이뤄진다.

## 결정적 투영

공개 투영은 정렬키가 고정된 canonical JSON으로 직렬화하고 SHA-256을 계산한다. 같은 원본 바이트·파서 버전·입력 계약이면 같은 `projection_sha256`을 생성해야 한다. 전문과 문장 단위 CSV는 `internal`, 공개 메타데이터는 `publish` 디렉터리에 분리한다.

## 10일 수집 주기

월별 cron 날짜를 직접 지정하지 않는다. 월 길이가 달라 정확한 10일 간격이 깨지기 때문이다. 작업은 매일 서울 시간에 한 번 기동하고 `2026-09-15`를 epoch로 하여 `2028-09-15`까지 경과일이 10의 배수일 때만 K-DATA 프로필을 실행한다. 수동 실행은 항상 허용한다.

2년 이력을 90일 Artifact에만 의존하지 않는다. 원문·전문·개인정보를 제외한 공개 해시 인덱스를 `snapshots/kdata/YYYY-MM-DD`에 커밋한다. 따라서 Git 이력만으로도 각 수집일의 원본 SHA-256, 정규화 전문 SHA-256, 투영 SHA-256 및 파서 버전을 대조할 수 있다. 원문과 전문은 공개 Git에 커밋하지 않는다.

## 기관 분리

- K-DATA 프로필만 이 저장소의 예약 작업에서 활성화한다.
- 신보 프로필 예시는 비활성 상태로 두며 이 저장소의 예약 작업에서 실행하지 않는다.
- 신보 운영은 신보 저장소에서 동일 runtime contract 버전을 고정해 별도로 배포한다.
- 기관별 원본, 전문, DB 행, GitHub Artifact, Supabase 환경변수를 공유하지 않는다.

## Supabase 경계

새 migration은 원격에만 있던 수집 테이블 4개를 Git의 기대 스키마로 기록하고, 파서 투영용 `document_projections`와 공개 전용 `publish` View를 정의한다. RLS는 활성화하되 정책과 권한을 자동 개방하지 않는다. 원격 스키마 drift와 타입·제약을 다시 읽기 전용 대조하고 승인받은 뒤에만 적용한다.

공개 View에는 전문, 수신자·작성자 이름, 로컬 저장 위치가 없다. `is_public=true` 및 인간 승인된 데이터만 공개 후보가 되며, 실제 브라우저 접근은 별도의 RLS 정책·권한 결정 전까지 차단한다.

## 검증 계약

- HWPX 전문 및 내부 용어 매칭
- DRMONE/FASOO 비우회 분기
- 원본·정규화·투영 SHA-256
- 같은 입력의 결정적 투영
- 내부 전문과 공개 투영의 디렉터리 분리
- 월 경계를 넘는 정확한 10일 주기
- 확장자가 틀려도 magic byte가 우선하는 형식 판정

## 보류 및 다음 행동

1. 실제 HWP·HWPX·PDF 표본으로 추출 품질 검산
2. OCR 엔진은 필요 문서의 빈도와 개인정보 처리 경계를 확인한 후 별도 결정
3. 원격 Supabase 4개 기존 테이블과 새 migration의 타입·제약 read-only 대조
4. 편집자·검토자·공개사용자별 RLS 정책 설계 및 계약 테스트
5. 2026-09-15 자료를 비공개 적재한 뒤 루브릭 기반 evaluation run 생성

이번 결정과 코드 구현 과정에서는 원격 Supabase를 변경하지 않았다.
