# 회의록 — Ollama 도입 유보 및 반복 검산 전환 조건

- 일자: 2026-09-12
- 대상: K-DATA Evidence Ledger
- 상태: 결정 채택, Ollama 미도입
- 공개 범위: 공개 저장소용 비식별 기록

## 1. 결정

### DEC-KD-016 — 현재 단계에서는 Ollama를 사용하지 않는다

K-DATA의 현재 판정량과 검산 빈도에서는 Ollama 연결이 필수적이지 않다. 우선순위는 PostgreSQL 제약조건, 버전된 산식, 게이트 함수, 롤백형 계약 테스트와 인간 검토로 판정 재현성을 닫는 것이다.

Ollama는 다음과 같은 반복 수요가 실제로 발생할 때 별도 검토한다.

- 같은 설명가능성 검사를 다수 주장 또는 CSV 행에 반복 적용해야 할 때
- 새 회신이 들어올 때마다 동일한 누락·상충 검사를 다시 수행해야 할 때
- 외부 모델로 보내지 않고 로컬에서 민감자료를 검사해야 할 때
- 반복적인 1차 검산이 Codex의 복잡한 구현·판정 검토 시간을 잠식할 때

단순히 로컬 모델을 사용할 수 있다는 이유만으로 도입하지 않는다.

## 2. 향후 도입 시 역할

Ollama는 판정 엔진이나 독립적인 사실판정자가 아니라 **로컬 설명가능성 린터**로만 사용한다.

허용 역할:

- 상태와 짧은 사유의 모순 후보 탐지
- 실패 게이트와 미확보 증거 코드의 대응 누락 탐지
- 증거번호 누락·중복·공통기원 후보 탐지
- 확정·추정·미평가 표현 혼합 후보 탐지
- 공개용 출력의 개인정보 노출 후보 탐지

금지 역할:

- `status_code` 또는 현재 판정 캐시 직접 변경
- 증거 진본성·법적 책임·인과관계의 최종 확정
- 원문에 없는 확률 또는 사실 생성
- Supabase 관리자 권한을 이용한 자동 수정

최종 상태 산출 경로는 계속 `ledger.derive_status_for_run()` 하나로 유지한다.

## 3. 도입 전 고정할 검산 방식

Ollama를 실행하기 전에 다음을 코드와 문서로 먼저 확정한다.

1. **검사 정의**: 검사별 입력 필드, 탐지 대상, 예외와 실패 의미를 정의한다.
2. **엄격한 출력 스키마**: 자유문 대신 주장 ID, 게이트 코드, 증거번호, 누락코드, 근거문을 가진 JSON만 허용한다.
3. **고정 실행조건**: 모델명뿐 아니라 모델 digest, 프롬프트 버전, 온도와 입력 해시를 기록한다.
4. **골든 케이스**: 정상·누락·상충·중복·미평가 사례와 기대 출력을 만든다.
5. **불변성 검사**: 무관한 문장순서나 점수 변화가 게이트 제안 결과를 바꾸지 않아야 하는 사례를 둔다.
6. **섀도 모드**: 결과를 DB 판정에 반영하지 않고 인간 판정과 나란히 비교한다.
7. **오류 검토**: 거짓 양성·거짓 음성과 근거 없는 코드 제안을 기록하고 수용 가능성이 확인된 검사만 반복 실행한다.
8. **승인 후 배치화**: 검증된 검사만 로컬 명령 또는 예약 작업으로 실행한다.

## 4. 결과 저장 원칙

향후 검산 결과를 저장할 경우 최소한 다음 재현정보를 남긴다.

```text
verification_run_id
claim_id
provider
model_name
model_digest
prompt_version
input_hash
output_json
schema_valid
suggested_gate_results
disagreement_codes
explanation_complete
human_review_status
started_at
completed_at
```

Ollama 출력은 평가 입력 후보 또는 검토 메모일 뿐 판정 원본이 아니다. 화면에는 인간이 승인한 검산 결과만 표시하고, 변경 시 기존 실행을 덮어쓰지 않는다.

## 5. 배치 위치와 보안

- Ollama는 Netlify 브라우저 화면에서 직접 호출하지 않는다.
- 로컬 컴퓨터의 Ollama 포트를 인터넷에 공개하지 않는다.
- 초기 도입은 로컬 명령으로 실행하며, 자동화가 필요하면 별도로 통제되는 실행 환경을 사용한다.
- 서비스 역할 키와 DB 접속정보는 저장소에 기록하지 않는다.
- 원본 사건자료 대신 필요한 최소 필드와 증거 식별자를 입력으로 사용한다.

## 6. 현재 작업 순서

1. Supabase 마이그레이션과 계약 테스트의 결정론적 검산 완료
2. 화면 상수를 DB 평가실행으로 이전
3. CSV와 상세 설명 화면 연결
4. 실제 반복 검산 비용과 빈도 측정
5. 반복 수요가 확인된 검사에 한해 Ollama 도입안 작성

현재 backlog에는 Ollama 구현 작업을 넣지 않고, 위 전환 조건 충족 여부만 추적한다.
